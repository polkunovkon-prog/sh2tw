# 00. Протокол исполнителя (обязателен к прочтению перед первой задачей)

Исполнитель: агент **Hermes** (оркестратор, инструменты файловой системы и запуска команд) + локальная модель **Qwen 3 8B, квантование IQ3_S** (генерация кода и текста). Заказчик/плейтестер: **Константин** (человек). Облачная модель привлекается человеком для консультаций — не агентом.

## 0.1. Почему этот протокол существует

IQ3_S — агрессивное квантование: модель склонна к пропуску деталей контекста, «забыванию» принятых решений внутри длинной сессии и уверенным галлюцинациям на незнакомых данных. Протокол компенсирует это тремя механизмами: **атомарными задачами**, **внешней памятью** (файлы состояния, а не память модели) и **машинными проверками** (тесты вместо «мне кажется, что работает»). Нарушение протокола — главный источник брака в этом проекте.

## 0.2. Правила контекста

1. **Не читать весь пакет ТЗ целиком никогда.** На задачу читаются только файлы из её карточки (`task_registry.json`, поле `spec_refs`) плюс `03_kontrakty_dannyh.md`, если задача создаёт или меняет файлы данных.
2. **Перед каждой правкой файла — перечитать его текущую версию с диска.** Не полагаться на воспоминания о предыдущем чтении: они могут относиться к другой сессии.
3. **Состояние проекта — на диске, не в голове.** Что сделано/делается/далее — только `PROGRESS.md`, `QUESTIONS.md` и `task_registry.json`.
4. Один рабочий цикл = одна задача из реестра. Переключение задач без закрытия текущей запрещено (исключение — блокирующий вопрос в `QUESTIONS.md`).
5. Если файл спецификации противоречит памяти модели — верит файл. Если два файла спецификации противоречат друг другу — стоп, вопрос в `QUESTIONS.md`, задача приостановлена.

## 0.3. Жизненный цикл задачи

```
ВЫБОР → ЧТЕНИЕ → ПЛАН → РЕАЛИЗАЦИЯ → САМОПРОВЕРКА → ОТЧЁТ → (РЕВЬЮ ЧЕЛОВЕКА) → ЗАКРЫТИЕ
```

1. **ВЫБОР.** Взять из `task_registry.json` первую задачу со статусом `pending`, у которой все `depends` закрыты. Перевести в `in_progress` (правка реестра).
2. **ЧТЕНИЕ.** Прочитать файлы из `spec_refs` задачи; прочитать затрагиваемые исходники.
3. **ПЛАН.** Записать в `PROGRESS.md` под датой: ID задачи, что делаю, какие файлы создам/изменю, как проверю. План из 3–8 пунктов. Если план не формулируется — задача слишком велика или не хватает данных: вопрос в `QUESTIONS.md`.
4. **РЕАЛИЗАЦИЯ.** Писать код/файлы по плану. Отступления от плана — только с записью причины в `PROGRESS.md`.
5. **САМОПРОВЕРКА.** Выполнить ВСЕ команды из поля `acceptance_cmd` карточки задачи. Все должны пройти. Если команда падает — чинить до прохождения; «закомментировать тест» не допускается.
6. **ОТЧЁТ.** В `PROGRESS.md`: сделано/не сделано, результаты проверок (вставить вывод команд), созданные файлы, отклонения от плана. Git-коммит (см. 0.6).
7. **ЗАКРЫТИЕ.** Статус `done` в реестре. Задачи с флагом `human_review: true` (геймплейные решения, баланс, всё связанное с игрой живьём) ждут отметки человека.

## 0.4. Антигаллюцинационный протокол (критично)

Разрешённые источники фактов, в порядке приоритета:

1. Файлы самого ТЗ (данный пакет).
2. Локальная копия документации OpenSH2: каталог `ref/OpenSH2-Notes/` (человек клонирует репозиторий `github.com/nox7/OpenSH2`, папка `Notes/` — задача S0.1). Ссылки вида `[OpenSH2:Notes/FileFormats/...]` указывают путь внутри неё.
3. Файлы игры в каталоге установки (парсить, мерить, сравнивать — первые руки).
4. Таблицы `13_prilozheniya.md` (реестр фактов с пометками достоверности).
5. Экспериментальные отчёты `experiments/reports/V*.json`.

Всё, что не найдено в 1–5, считается **неизвестным**. Запрещено: придумывать смещения байт, ID объектов, параметры триггеров, имена функций игры, размеры структур «по логике». Правильное действие при неизвестном — сформулировать минимальный эксперимент (как в файле 10) или вопрос в `QUESTIONS.md`. В коде неизвестное помечается комментарием `# UNKNOWN(<что именно>): <как закрываем>` и не используется в логике до закрытия.

Каждый новый факт, добытый из игры или эксперимента, записывается в `13_prilozheniya.md` (раздел J, реестр фактов) с пометкой источника — пакет ТЗ живёт и пополняется.

## 0.5. Стандарты кода

- Python 3.11+, только x64 Windows-совместимый код (игра и все инструменты — Windows). Пути — через `pathlib.Path`. Кодировка всех файлов — UTF-8 (в коде, читающем игровые файлы, работать с `bytes`; не декодировать бинарные данные).
- Внешние зависимости минимизируются. Разрешённый базис: `pytest`, `PyYAML`, `fastapi`, `uvicorn` (оболочка), `pillow` + `pytesseract` (опционально, OCR), `watchdog` (опционально; допустим поллинг). Всё остальное — по согласованию с человеком.
- Модуль ≤ 400 строк, функция ≤ 50 строк, без метапрограммирования и «умного» кода. Явное лучше неявного: длинные понятные имена, никаких однострочных трюков.
- Типизация аннотациями обязательна для публичных функций. Docstring — 1–3 строки: что делает, что возвращает, кидает ли исключения.
- Ошибки: свои исключения с внятными сообщениями (`class Sh2ParseError(Exception)`), без молчаливых `except: pass`.
- Один переносимый принцип: **бинарные данные игры никогда не модифицируются на месте** — только чтение из каталога игры, запись в каталог проекта (исключения и порядок — в 0.7).

## 0.6. Git и журнал

- Репозиторий проекта — `sh2tw/` (структура в 02). Коммит на каждую закрытую задачу: формат `[S<этап>.<задача>] краткое описание` (пример: `[S2.3] object tree walker + round-trip test`).
- `PROGRESS.md` ведётся append-only (новая запись сверху, старые не правятся). `QUESTIONS.md` — список открытых вопросов с датой, ID задачи и статусом (open/answered).
- Бинарные артефакты (карты, сейвы, dll) в git не коммитятся, кроме эталонных образцов из `templates/` (см. 05) — их коммитим.

## 0.7. Безопасность каталога игры

- Каталог игры (путь в `config/project.ini`, ключ `game_dir`) — **чужая территория**. Разрешено: чтение любых файлов; запись сгенерированных карт в `Maps/` с префиксом `S2TW_`; установка/удаление файлов трека 2 (только после V5, только скриптами `install_bridge.py`/`remove_bridge.py` с бэкапом).
- Перед первым запуском любого кода, меняющего `Maps/`, выполняется `tools/backup_maps.py` (полная копия каталога в `backup/maps_<дата>/`).
- Сейвы: только чтение (`Documents/Stronghold 2/Saves/`). Автосейвы игры не удалять и не перезаписывать; рабочие копии — в проект.
- Любой скрипт, трогающий каталог игры, обязан иметь ключ `--dry-run` и печатать список изменений до их применения.

## 0.8. Разделение с человеком

Человек делает всё, что требует живой игры и вкуса: плейтесты, эксперименты V-серии, геймплейные решения, приём задач с `human_review: true`, финальные правки баланса. Агент делает весь код, парсеры, генераторы, тесты, документацию, разбор файлов. **Агент не запускает игру сам**, кроме случаев, когда эксперименты V1/V2/V4 закрыли автоматический запуск (и тогда — только через скрипты раннера с `--dry-run`-проверкой).

Облачная модель (по запросу человека): ревью спорных кусков, помощь при блокировках, обновление ТЗ. Агент готовит для этого «пакет контекста» (что делаем, что не получается, вывод ошибок) — человек копирует его в чат с облаком.

## 0.9. Эскалация и стоп-условия

- 3 неудачные попытки решить подзадачу → запись в `QUESTIONS.md` со всеми деталями (что пробовал, вывод ошибок) → переход к другой незаблокированной задаче, если есть.
- Любое сомнение в интерпретации формата → не продолжать «наугад»; это проект по точной бинарной работе.
- Обнаружено противоречие между поведением игры и реестром фактов → стоп, зафиксировать в реестре как новый факт с пометкой «противоречит §…, проверить человеку».

## 0.10. Чек-лист перед закрытием любой задачи

- [ ] Все команды `acceptance_cmd` прошли; выводы приложены в `PROGRESS.md`.
- [ ] Ни одного маркера `UNKNOWN(...)` без записи в `QUESTIONS.md`.
- [ ] Новые/изменённые форматы данных согласованы с `03_kontrakty_dannyh.md` (или изменение задокументировано).
- [ ] `pytest` по всему проекту зелёный (не только новые тесты).
- [ ] Коммит сделан, реестр задач обновлён, `PROGRESS.md` заполнен.
- [ ] Если задача `human_review` — уведомлён человек, задача в статусе `awaiting_review`.
