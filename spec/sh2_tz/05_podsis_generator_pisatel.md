# 05. Подсистема: генератор сцен и писатель карт (K2, K3)

## 5.1. Назначение

Превращает `scene_spec.json` в готовую к запуску карту `Maps/S2TW_<scene_id>_<type>.s2m`, запускает её, ловит завершение и собирает `scene_result.json`. Три уровня мощности, каждый следующий включается только при провале предыдущего:

| Уровень | Механизм | Что даёт | Риск |
|---|---|---|---|
| **L1. Патчер** | равнодлинные байтовые правки заготовки по якорям | старт-ресурсы, таймеры, флаги миссии, числа стартовых войск в готовых слотах | минимальный |
| **L2. Писатель MapHeader** | полная пересборка сегмента MapHeader из модели; RadarMap и S2Game копируются байт-в-байт | любые EstateMarkers, Scenario, Mission, ScenarioEvent, стартовые войска, конфигурация лордов | средний |
| **L3. Rehost** | база карты = переименованный сейв (V4): S2Game несёт реальную застройку игрока | точный перенос замка в оборонительную сцену | зависит от V4 |

Лестница fallback: L1 → L2 (L2 включает L1 как частный случай) → L3 поверх L2 для оборон. Постройки из snapshot пересборкой S2Game **не занимаемся** (решение 02 §2.5).

## 5.2. Общий конвейер генерации

```
scene_spec.json
  → выбор базы: templates/maps/<template_id> ИЛИ rehost-снимок .sh2
  → load (парсер 04) во внутреннюю модель
  → применение overrides:
      sides/provision → Scenario (старт-ресурсы) + EstateStartupTroopPlacement (войска) + war_chest
      mission_events (DSL) → ScenarioEvent-записи
      alliances → Scenario/итоговые флаги
  → сборка: MapHeader из модели; RadarMap/S2Game — исходные байты
  → контр-проверки: provision_balance(spec) (честность, 04 §4.5);
     struct-валидаторы (длины, энумы через ref/enums, уникальность якорей)
  → атомарная запись Maps/S2TW_<id>_<type>.s2m + sателлит .build.json (что и откуда собрано)
  → опционально: удаление прошлых S2TW_-карт (cleanup-maps)
```

## 5.3. Патчер (L1)

DSL манифеста — 03 §3.8. Движок:

```python
def apply_patches(segment: bytes, manifest: PatchManifest) -> bytes:
    """Применяет патчи строго по порядку; любой конфликт — исключение."""
    for p in manifest.patches:
        positions = find_all(segment, bytes.fromhex(p.anchor_hex))
        if len(positions) != 1: raise PatchAnchorError(p.id, len(positions))
        off = positions[0] + len(p.anchor) + p.anchor_offset
        if segment[off:off+len(p.expected)] != p.expected: raise PatchMismatchError(p.id, diff=...)
        segment = segment[:off] + p.new + segment[off+len(p.new):]
    return segment
```

Гарантии: равнодлинность проверяется на этапе загрузки манифеста; после применения — повторный `load` парсером и сверка round-trip новой карты (нестрого: файл собран нами, эталон — новая карта).

**Процедура разработки патча** (регламент для агента, задача выполняется на копиях, никогда на оригиналах):

1. Скопировать эталон шаблона в `work/`.
2. Изменить одно поле в редакторе игры (например, стартовое золото стороны 0: 10000 → 24000; данные о поле — из spec-задачи).
3. `python -m sh2tw.cli diff-maps original.s2m edited.s2m` — показать изменённые байты с контекстом (±16 байт), по сегментам.
4. Выбрать уникальный якорь в контексте (проверка: встречается 1 раз), записать патч в манифест с `expected_hex` = старое значение.
5. Подтвердить: `build` с новым патчем → загрузка в игру (человек) → поле изменилось.
6. Двухшаговая валидация смысла: значение в snapshot после parse совпадает с ожидаемым.

Типовые патчи этапа 3 (приоритет разработки): стартовое золото/ресурсы по сторонам (Scenario); стартовые войска эстейтов (EstateStartupTroopPlacement — типы/количества в слотах); параметры Invasion-записей (типы/числа в готовых событиях); таймеры (TimeUntilFinalInvasion); флаги победы/поражения; позиции EstateMarkers (равнодлинные, 32 слота × 12 байт — F8).

**Граница равнодлинного патчинга** (ответ на вопрос 2 плана §10): равнодлинно патчатся все поля фиксированной ширины в существующих записях; НЕ патчатся: добавление/удаление записей (событий, слотов войск, лордов), изменение длин строк, любая правка S2Game. Добавление/удаление — территория писателя L2.

## 5.4. DSL событий → ScenarioEvent

`mission_events` из scene_spec компилируются в записи ScenarioEvent. Структуру записи и кодирование ID триггеров/действий брать из [OpenSH2:ScenarioEvent.md] + списки Приложений A/B (13) + попарные hexdiff'ы карт, сохранённых из редактора с одним добавленным событием (та же процедура, что 5.3 п.2–4). Поддерживаемый минимум DSL:

| Элемент DSL | Нативное средство | Примечание |
|---|---|---|
| `{"after_months": N, "action": "Invasion", params}` | Invasion | owner (сторона-владелец!), from/attack marker, troops, repeat — параметры подтверждены sd2 (23.11.2026) |
| `{"after_months": 0, "action": "ControlLordsAI", params}` | Control Lord's AI | включить/выключить ИИ конкретных лордов; основа AI-only сцен V1 |
| `{"trigger": {"type": "EnemyLordDead"}, "actions": [{"action": "Win"}]}` | Enemy Lord Dead → Win | победа сценария |
| `{"trigger": {"type": "LordDies"}, "actions": [{"action": "Lose"}]}` | Your Lord Dies → Lose | поражение |
| `{"trigger": {"type": "ControlNumEstates", "params": {"n": X}}, "actions": [{"action": "Win"}]}` | Control a Number of Estates → Win | условие захвата региона |
| `{"action": "PauseSieges", "params": {...}}` | Pause Sieges | мирные сцены развития |
| `{"action": "TakeEnemyCastle" / "ConvertEstateToVillage"}` | Take Enemy's Castle / Convert Estate to Village | пост-захват в сценах захвата региона |
| `{"action": "GiveGold"/"GiveResources"/"GiveHonour"}` | Give Gold/Resources/Honour | военная казна (канал C) |
| `{"action": "SetAllies"}` | Set Allies | дипломатия внутри сцены |
| `{"action": "TimeUntilFinalInvasion", "params": {"months": N}}` | Time until Final Invasion | жёсткий тайм-аут сцены → Lose |

Маркеры (баннеры) 1–8 четырёх цветов — точки появления/атаки вторжений; на шаблонах маркеры расставляет человек в редакторе (по регламенту задачи S3.1), генератор ссылается на их номера.

## 5.5. Писатель MapHeader (L2)

`map_header_writer.py` собирает MapHeader-сегмент из модели (парсер 04 обязан уметь сериализовать): объектное дерево сегмента (маркеры F2), EstateMarkers-массив, Scenario, Mission, ScenarioEvent-блоки, EstateStartupTroopPlacement. RadarMap и S2Game — «прозрачно» из шаблона. Уровень zlib — из `.meta.json` шаблона.

Обязательные валидации после сборки (автоматические): (1) `load` собранного файла парсером — без ошибок; (2) повторная round-trip сборка из распарсенной модели — байт-идентична (фиксирует детерминизм сериализатора); (3) энумы лордов только из `ref/enums/`; (4) сумма слотов EstateMarkers ≤ лимита доки; (5) `provision_balance` (честность) — pass до записи.

Эталонная планка писателя: на 5 ванильных картах построить модель из `load` и собрать — байт-идентичность (это закрывает вопрос «сериализация ровно обратна парсингу»). Расхождение = баг либо пропуск поля модели — чинить до полного совпадения.

## 5.6. Rehost (L3)

Если V4 подтверждён: `rehost.py` берёт сейв сцены развития региона (`last_theater_snapshot` региона), переименовывает/оборачивает в `.s2m` (точная процедура — по итогам V4: расширение, правка полей заголовка при необходимости), затем писатель L2 **переписывает MapHeader** под оборонительную сцену (войска атакующего, события, Win/Lose), не трогая S2Game с реальной застройкой. Fallback при провале V4: шаблоны уровней застройки (5 уровней × географии, библиотека S3.1) — оборона на обобщённой геометрии уровня.

## 5.7. Раннер сцены (K3)

```
sh2tw/runner/
  launcher.py        # запуск игры с картой
  saves_watcher.py   # слежение за Saves/ (поллинг 2 с)
  outcome.py         # лестница детекта исхода
  watchdog.py        # краш-контроль процесса
```

**Запуск (лестница, закрывается V2):** (a) `os.startfile(map)` — если ассоциация `.s2m` зарегистрирована (Steam-установка); (b) запуск `Stronghold2.exe` + человек выбирает карту в меню (карта гарантированно в списке — имя `S2TW_…` сортируется в начало; трек 2 добавит автозагрузку); (c) AutoHotkey-скрипт нажатий (последний fallback, только с согласия человека).

**Детект завершения:** процесс игры завершился (poll `psutil`/`tasklist`) → интервал ≥ 90 с стабилен.

**Детект исхода (лестница, закрывается V3):**

1. **Мост (трек 2, если включён):** файл `bridge/outcome.json` от d3d9-моста — точный исход и автосейв.
2. **Парс автосейва:** новейший `.sh2` с mtime > старта сцены → `snapshot` → сравнение со стартовым: `lord_died(lord)` + смена владельцев эстейтов + выжившие войска. Правила: `win` если мёртв вражеский лорд (или выполнен ControlNumEstates ≥ цели) и жив свой; `loss` наоборот; неоднозначное (оба живы, тайм-аут) → draw/aborted по таймеру сцены.
3. **OCR экрана (V3c):** периодический скриншот окна (в момент, когда заголовок/состояние меняется на послебоевой) → pytesseract → слова «Victory/Победа/Defeat/Поражение». Реализация только если V3c покажет ≥ 95 % точности на 10 тестах.
4. **Ручной ввод (всегда доступен):** оболочка показывает экран «Исход?» с кнопками Win/Loss/Draw + авто-предложение из п.2; потери добираются из snapshot'а. Стоит ≤ 10 секунд человека — это штатный fallback, не стыдный.

**Watchdog:** если игра упала (код ≠ 0) — сцена помечается `aborted`, crash-лог (папка Saves, время, код) в `scene_result.anomalies`; армия игрока возвращается в кампанию без потерь (правило милосердия, см. 07 §7.7).

## 5.8. Библиотека шаблонов

Источник — 89 карт копии заказчика (реестр снимается задачей S3.0 `catalog-maps`: тип, размер, число лордов, эстейты, маркеры, пригодность). Отбор: 6–10 карт под роли: 2 полевых (равнина, река), 3 штурмовых (замок в центре / на холме / у cliffs), 2–3 заготовки театра (kingmaker, 4–8 эстейтов), 1–2 specialty. Для каждой: человек открывает в редакторе, расставляет маркеры вторжений (1–8) и сохраняет эталон; эталон хэшируется, копия — в `templates/maps/` (в git), манифест патчей — рядом.

Карты-кандидаты из копии (финальный отбор за человеком): Strong and Stable, Two Pronged Crown, Whitebear — упомянуты планом как стартовые для этапа 0; полный список — по каталогу.

## 5.9. Тесты и приёмка

- Юнит: патчер на синтетических буферах (якорь не найден / найден дважды / mismatch — все дают исключения); DSL-компилятор — golden-тесты пар «spec → байты ScenarioEvent».
- Интеграционные: сборка каждой из 4 типов сцен на шаблонах → `load` парсером → все валидации зелёные.
- Эталонные: писатель round-trip на 5 ванильных картах (5.5).
- Живые (человек): карта грузится в игре; 10-минутный прогон не крашится; поля, заданные спеком, реально изменились (проверка по snapshot после старта). Формализовано в V12.
- Генерация ≤ 30 с на карту (производительность).

## 5.10. Известные ловушки

- Не генерировать карты в подпапку `Maps/` — игра может не сканировать подпапки (проверить в V2b; до того — только корень `Maps/`).
- Имя карты ≤ 27–30 символов (практика редактора; длинные имена обрезаются — проверить).
- Валидация писателя «load-able» ≠ «playable»: обязательны живые тесты V12.
- `lastsave`/версия в заголовке файла: при сборке новых карт проставлять согласованные значения (какие именно — hexdiff'ом с картами, сохранёнными редактором; вопрос в QUESTIONS.md при расхождении).
- Триггеры убийства лордов — только через таблицу энумов (F9!): тест-карта «убийца/жертва» на каждой паре лордов (V8) до первого использования в бою.
