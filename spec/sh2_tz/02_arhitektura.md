# 02. Архитектура

## 2.1. Решение (вариант «G», принято предварительным планом)

Внешняя оболочка кампании + дискретный генератор сцен + опциональный хук-мост. Стратегический слой живёт вне игры; каждая битва/сеанс развития — отдельная сцена SH2, генерируемая из файлов-заготовок и снимков состояния; итоги читаются из сейвов. Двухтрековая схема:

- **Трек 1 (ядро, файловый):** только чтение/запись файлов игры. Не зависит от билда и версии. Обязателен.
- **Трек 2 (опциональный, двоичный):** прокси-`d3d9.dll` поверх sh2-unofficial-patch (через `d3d9_chain.dll`) — телеметрия, программный автосейв, автозапуск. Включается только после успеха V5 (совпадение билда репака с Steam v1.5.0). Система обязана полностью работать без него.

Почему не «одна гигантская карта» и не «своя карта каждому боту с постоянными прогонами» — зафиксировано в §3 предварительного плана (F3: жёсткие 256×256 высот; G1: максимум 8 сторон; отсутствие структуры ходов; 32-битный движок). Пересмотру не подлежит; долгосрочная альтернатива — этап D (OpenSH2).

## 2.3. Конвейер сцены (главный поток данных)

```
ОБОЛОЧКА                ГЕНЕРАТОР                ИГРА (человек)            ПАРСЕР
   │ scene_spec.json ─────▶│                            │                     ▲
   │                       │ выбор шаблона/снимка       │                     │
   │                       │ применение патчей          │                     │
   │                       │ сборка MapHeader (писатель)│                     │
   │                       │ запись Maps/S2TW_*.s2m     │                     │
   │ запустить сцену ─────────────────────────────▶ запуск, игра             │
   │                       │                            │  автосейвы .sh2 ────┤
   │                       │                            │  (выход/победа)     │
   │ детект завершения ◀── watcher Saves/ + процесс ───┘                     │
   │ ◀── scene_result.json (исход, потери, ветераны) ────────────────────────┘
   │ применение итогов к campaign_state.json
```

Шаги: (1) оболочка формирует `scene_spec.json`; (2) генератор выбирает источник карты (шаблон или rehost-снимок), применяет равнодлинные патчи и/или пересобирает MapHeader; (3) раннер запускает игру; (4) watcher следит за `Documents/Stronghold 2/Saves/`; (5) после выхода из игры парсер берёт новейший релевантный сейв → `snapshot.json` → сравнение со стартовым снимком → `scene_result.json`; (6) оболочка применяет итоги. Детект исхода — лестница каналов (07 §7.6): автосейв-парс → OCR экрана → ручной ввод (1 клик).

## 2.4. Провижининг армий (как войска попадают в сцену)

Проблема: армия кампании — роспись `{тип юнита × количество × ветеранство}`; сцене SH2 нужны либо юниты на карте, либо ресурсы на найм. Три канала, приоритет закрывает эксперимент V7:

| Канал | Механизм | Достоинства | Ограничения | Статус |
|---|---|---|---|---|
| **A. Стартовые войска эстейта** | MapHeader-поле `EstateStartupTroopPlacement` [OpenSH2:Notes/FileFormats/S2M/MapHeaderSegment/EstateStartupTroopPlacement.md] — стартовые войска прописываются карте по эстейтам; редактор даёт их выставлять, значит формат поддерживает | Точная роспись под контролем; работает для обеих сторон | Фиксированное число слотов/типов (уточнить в доке и V7); требует писателя MapHeader | Основной кандидат |
| **B. Invasion с указанием владельца** | Событие Invasion: «near-exact numbers of troops, which player owns it, where it begins and attacks, who it is attacking/reinforcing, repeat» (sd2, подтверждено 23.11.2026) | Нативная механика; волны, тайминги, повтор; войска появляются в нужном месте | Скорее для атакующих/подкреплений; контроль игрока над Invasion-войсками проверить в V7 | Основной кандидат |
| **C. Военная казна** | Стартовое золото+честь (патч Scenario) + наёмный пост (юниты только за золото — fandom, подтверждено 23.11.2026) и/или казармы с предзапасённым оружием | Простота; игрок сам выбирает состав в первые минуты сцены | Тратит игровое время сцены; наёмный пост — спецюниты (ассасины и пр.), не вся роспись; требует V7 | Fallback / смешанный |

Правила: (1) ветераны (уровень выслуги в кампании) в сцене отображаются +N % к «казначейской стоимости» канала C либо просто сохраняются списком выживших; в SH2 нет юнит-опыта (проверено 23.11.2026, fandom Barracks — ветеранство ведёт оболочка); (2) лимит юнитов сцены ≈ 550 на сторону при 2 сторонах (G6, формула 300+floor(500/n)) — росписи кампании ограничить 200 юнитами на армию; (3) стоимость росписи в золоте = Σ(цена найма юнита) — единая валюта баланса для авто-резолва и канала C.

## 2.5. Перенос застройки региона (оброны на своей земле)

| Способ | Механизм | Качество | Статус |
|---|---|---|---|
| **Rehost-снимок** | Сейв сцены развития региона → переименование в `.s2m` → база оборонительной сцены: замок игрока ровно такой, каким он его отстроил | Идеальная точность | V4 закрывает |
| **Шаблоны уровней** | Библиотека эталонных карт: 5 уровней замка × географии; оборона идёт на шаблоне уровня застройки региона | Средняя (геометрия обобщена) | Fallback, работает всегда |
| **Полный писатель S2Game** | Сборка объектного дерева (постройки) из snapshot | Максимальная | НЕ делаем (за рамками; только если этап D) |

Граница: **писатель работает только на уровне MapHeader** (EstateMarkers, Scenario, Mission, ScenarioEvent, стартовые войска); сегменты RadarMap и S2Game всегда копируются из шаблона/снимка байт-в-байт. Постройки игрока переносятся rehost'ом, не пересборкой.

## 2.6. Режим «развитие-театр» (объединение театра и развития)

Театр и сцена развития — **один тип сцены** (`development`): kingmaker/war-custom карта с эстейтом игрока и 4–6 живыми лордами-соседями (ControlLordsAI на всех, включая лорда игрока — нет, игрок играет сам; см. ниже), ограниченная длительность (24–36 игровых месяцев), PauseSieges по желанию (мирная сцена развития) или управляемые осады.

- Игрок строит свой регион руками; ИИ-соседи развиваются по-настоящему рядом (живая экономика).
- Итог: snapshot → (a) постройки игрока → уровень застройки региона + будущий rehost-замок; (b) дельты ИИ → их состояния в кампании; (c) события (кто на кого напал) → лента журнала.
- Частота: не чаще 1 раза в 2–3 сезона (кулдаун в `campaign_state.json`); между театрами развитие ИИ считается внешней моделью «план .aic + время» (детерминированная оценка по таблицам этапа 5).
- Лимит сторон театра ставит V6 (цель: 6–7 лордов на Large карте, 30 игровых месяцев без деградации FPS/памяти; fallback 4–5).

## 2.8. Технологический стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Язык ядра | Python 3.11+, stdlib-first | Слабой модели проще писать и отлаживать; бинарная работа через `bytes`/`struct`/`zlib` достаточна |
| Оболочка | FastAPI + uvicorn (localhost:8402) + одностраничный HTML/JS (без фреймворков) | Проще отлаживать, скриншот-тесты, никакого билд-степа |
| Данные | JSON (состояние, контракты), YAML (доктрины, GA-конфиг), JSONL (журнал событий) | Git-friendly, диффается, читается человеком; SQLite — нет (решение зафиксировано, см. файл 12) |
| Тесты | pytest; corpus-тесты round-trip на 89 картах + 78 сейвах копии заказчика | P8 |
| OCR (опция) | pillow + pytesseract (только для детекта исхода, канал V3c) | Локально, без сети |
| GA-параллелизм | 2–3 инстанса игры через Sandboxie-Plus, раннер-пул с watchdog | 32-битный процесс: следить за памятью (V6) |
| Трек 2 | C++ (MSVC 2019, x86), прокси-d3d9 поверх sh2-unofficial-patch v0.9.0 через d3d9_chain | Единственный совместимый способ (G6/G7: две прокси конфликтуют, только цепочкой) |

## 2.9. Потоки данных и владение файлами

- Единственный владелец игрового состояния — оболочка (`campaign_state.json`); генератор и парсер без состояния (вход → выход).
- Все файлы контрактов версионируются полем `schema_version` (см. 03); читатель обязан отвергать неизвестную мажорную версию.
- Журнал: `campaigns/main/events.jsonl` — append-only запись каждого применённого итога/решения (аудит и undo).

## 2.10. Соответствие ограничениям движка (контрольный список дизайна)

| Ограничение | Значение | Как соблюдаем |
|---|---|---|
| Сторон в сцене | ≤8 (G1) | Сцены проектируются на 2–3 стороны; театр ≤7 лордов |
| Лордов в MapHeader | до 16 (F8) | Кампания 5–7 лордов + нейтралы |
| EstateMarkers | 32 слота × 12 байт (F8, уточнить по доке) | Регионов 12–16 + деревни; следить за лимитом при генерации |
| Юнитов на сторону | ~550 (2 стороны, G6) | Росписи ≤200 |
| Время | 1 месяц ≈ 1 мин (G2; V5b меряет множители `+/−` на numpad) | Сцены 20–45 мин = 20–45 месяцев; театр 24–36 месяцев |
| Высоты карты | 256×256 фиксировано (F3) | Никогда не трогаем; география только из заготовок |
| Состояние между миссиями | переносится нативно (F7) | Используем rehost вместо (V4) — проще и надёжнее |
